# ADR-0004: Distribution — browser/PWA via pc-setup, no desktop shell

- Status: Superseded by ADR-0005
- Date: 2026-11-22

## Context

Targets are macOS and Windows 11 only. The GUI must start, connect to herdr,
report version and install state verifiably, and be installable/updatable
from `rebuildup/pc-setup`'s existing bootstrap flow (mise / Homebrew / WinGet
/ app management). Linux stays on the herdr TUI.

## Decision

- The product ships as a **local web app**: a Bun bridge process serves the
  built static UI and the `/api` + `/ws` endpoints on `127.0.0.1` (default
  port 4737, `PORT` override). The user opens it in a browser; it is
  PWA-installable.
- **No Electron/Tauri wrapper, no resident service, no second daemon.** The
  bridge starts on demand (`bun run start` / pc-setup managed launch) and
  exits with the session. herdr itself remains the only long-lived process.
- Installation is source-based, matching pc-setup's model: a managed git
  clone under the platform's source root, `mise install --locked` +
  `bun install`, and a per-OS launch path (macOS: login item / `open`;
  Windows 11: Startup folder or `pc-setup` converge entry). The exact
  mechanism is decided in the pc-setup integration issue; this ADR fixes
  only that the channel is "clone + bun", not a packaged binary.
- Version identity comes from `package.json#version` and the Git commit;
  `/api/health` exposes both for verify.
- Bootstrap must be re-runnable and must not touch herdr config, sessions,
  or credentials.

## Consequences

- "App" on each OS is a browser tab/PWA pointed at the local bridge; there is
  no separate native binary to sign or notarize.
- pc-setup gains a `herdr-t3` component with install + verify steps; Linux
  platform files are not touched.
- If a packaged desktop shell is ever wanted, it is a new ADR wrapping this
  same bridge — the bridge contract does not change.
