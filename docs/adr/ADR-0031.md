# ADR-0031: TextGen surface — textgen-v1 contract pin @d23205af and read-surface adoption

- Status: Accepted
- Date: 2026-11-28
- Program: issue #188 (T3 parity); ticket #442. Plugin-surface
  consumption of `rebuildup.textgen`; same ADR-0011 `plugin_call`
  boundary as ADR-0012/0014/0016/0026/0027/0028/0029.
- Pin: `rebuildup/herdr-plugins@d23205af0cd2ff7dba25f72e1f3b872762a108ee`
  = tag `v0.9.0`, contract `herdr-plugins.textgen/v1` (STABLE since
  herdr-plugins v0.6.0; plugin `rebuildup.textgen` v0.7.0+).
  Upstream spec: `herdr-plugins/docs/contracts/textgen-v1.md`.

## Context

The textgen plugin owns structured text generation: six task kinds
(`thread_title`, `branch_name`, `commit_message`, `pr_content`,
`review_guide`, `next_prompt`) executed through dedicated herdr
agent panes (agent path, ADR-0017 upstream) or opt-in HTTPS API
generators (ADR-0018 upstream), with pre-execution guards
(`requires_opt_in`, manifest availability, opt-in quota probe) and a
read-only `git-context` preview that collects repository input through
the rebuildup.git plugin without invoking a provider.

Two facts shape the surface. First, the contract advertises
`mutation_commands`: `generate` and `watch-next-prompt` drive herdr
agent panes and record pane metadata, and the `config` write
subcommands mutate config.json. Second — and unlike the issue's
initial sketch — the contract has NO list/history/result commands:
generation results are returned to the caller and never persisted
plugin-side, so there is no history to render and no result store to
review. Generation and application are contractually separated
(adopting a result is always the caller's job).

## Decision

1. Consume the READ commands `capability` and `git-context`.
   `capability` is the eager per-machine read (task×path matrix,
   agent/api provider matrix, guards, `integrations.git` status,
   redacted config, config warnings) and `git-context` is a lazy,
   submit-triggered preview of the collected task input — it invokes
   no provider. `config show` stays unconsumed: `capability` already
   carries the redacted config.
2. Mutations stay OUT. `TEXTGEN_MUTATION_COMMANDS` is an empty
   allowlist so `textgenSupportsMutation` fails closed even though
   the contract advertises `generate`/`watch-next-prompt`/`config`
   writes — a future generation ticket must extend the allowlist
   deliberately and design its own result retention/review flow,
   since the contract persists no results.
3. `src/shell/textgen.ts` mirrors the `artifacts.ts` store shape:
   per-machine `{status, capability, capabilityError}` state,
   defensive `*FromDoc` parsers that reject foreign contracts and
   malformed documents, the shared
   `not_installed|disabled|incompatible|unreachable|error`
   classification, a TTL-cached capability probe, and refresh on
   snapshot pushes (debounced), machine-status and machine-list
   changes via `initTextgen()`. A capability failure retains the
   last-good document.
4. Honesty rules rendered verbatim, never re-derived: task
   `requires_opt_in` badges with the plugin's opt-in explanation,
   provider `availability` (`manifest`/`not_in_manifests`/`unverified`)
   and `warning`, API `credential_configured` booleans (key material
   never crosses the bridge), `integrations.git` resolved/unavailable
   with `error`, `config_warnings`, guard settings, and `cli` path
   `unsupported` status. No tasks/providers/git integration render as
   explicit empty states.
5. `src/components/TextGenSurface.tsx` renders the registry with T3
   Code primitives and design tokens only; the git-context preview
   shows `repo_root`/`branch`/collected `input` (pretty JSON with a
   copy affordance), `sources` and `warnings` verbatim. The surface
   copy states plainly that generation results are never
   auto-applied.
6. Surface wiring follows the established right-panel pattern:
   `rightPanelStore` union + `isSurface`, `RightPanel`
   icons/titles/content/add-actions, `CommandMenu` and
   `WorkspaceHeader` entries, `initTextgen()` in `App.tsx`.

## Consequences

- The textgen gap narrows to "plugin-owned generation contract, GUI
  renders the read surface"; `generate`/`watch-next-prompt` UI,
  result review/retention, composer insertion of `next_prompt`
  candidates, and config editing remain future tickets with their own
  contract review.
- Because the contract persists no results, a generation ticket
  cannot offer "history" without new upstream state — recorded here
  so the next ticket does not assume a list command exists.
- Contract pin is recorded here and in
  `docs/migration/contracts/plugin-textgen.md` +
  `docs/migration/capabilities.json`; a future contract revision
  re-pins via a new ADR per the established rule.

## Amendment (issue #458, 2026-11-27): `generate` adopted, transient results

Decision 2 is superseded for `generate` only:

1. `TEXTGEN_MUTATION_COMMANDS` now allowlists `generate`. The surface
   offers task selection, a per-task input form built from the
   capability's `input_fields`/`required_input`, provider/model
   overrides, `--git-pane`/`--git-root` collection for the three git
   tasks, optional `--cwd`/`--timeout`, and `--allow-expensive` for
   `requires_opt_in` tasks. Every run goes through a confirm dialog;
   `watch-next-prompt` and the `config` writes remain gated off.
2. Task input travels on the plugin CLI's **stdin** via a new
   `plugin_call.stdin` field (bounded 256 KiB, protocol-validated,
   plumbed through `PluginExecOptions` on both the local spawn and
   the ssh host; stdin is always closed immediately so stdin-reading
   CLIs see EOF). Rationale: the contract reads input from
   stdin/`--input FILE`, and `plugin_call` is argv-only — stdin is
   the only portable payload channel. `plugin_call.timeout_ms` was
   raised to a 600 s ceiling to cover the agent path's per-task
   defaults (`review_guide` 600 s).
3. Results stay **transient**: the contract persists nothing, so the
   surface renders the latest result once with a "not retained"
   badge and a copy affordance, and states plainly that history does
   not exist. Generation and application remain separated — nothing
   is auto-applied. The retention gap is recorded upstream as
   rebuildup/herdr-plugins#249; if a retention contract lands, a
   follow-up ticket can add history/review without changing this
   surface's generate path.
