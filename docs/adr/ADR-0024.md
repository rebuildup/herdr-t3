# ADR-0024: Checkpoints — checkpoints-v1 re-pin @ae4f214 and save/restore-group/gc/prune adoption

- Status: Accepted
- Date: 2026-11-26
- Amends: ADR-0016/ADR-0017/ADR-0021 (checkpoints-v1 adoption point);
  same re-pin rule as ADR-0012/ADR-0015/ADR-0018/ADR-0019/ADR-0020/ADR-0021.
- Program: issue #188; ticket #279. Upstream:
  rebuildup/herdr-plugins#75 (multi-repo groups + retention GC) and
  #94 (honest gc/prune exit codes, plugin version 0.4.0), merged to
  release-0-4-0 @ `ae4f214`.

## Context

`docs/contracts/checkpoints-v1.md` advanced after the ADR-0021 pin
(`55df8d0a`). The contract gained multi-repo checkpoint groups and
bounded retention:

- `save` captures one checkpoint per resolved repo under a shared
  `group_id` (`grp-…`). Repo set resolution: repeated `--repo PATH`
  flags, a pane target (`--pane`/positional/`HERDR_PANE_ID`/plugin
  context), or — with neither — live discovery across every distinct
  repo resolved from the session snapshot's pane cwds (non-repo cwds
  reported in `skipped_panes`; unreachable session →
  `session_unreachable`). `list` gains `--group` and entries gain
  `group_id` (save captures only).
- `restore-group <group-id> [--force]` restores every state entry
  with the matching `group_id`, per-repo through the full restore
  pipeline; `--repo` is rejected; unknown id → `unknown_group`.
- `gc` enforces bounded retention (`--max-count` default 50,
  `--max-age-days` default 30, `pre_restore` entries younger than
  `--protect-days` default 7 exempt); `prune` deletes hidden refs no
  state entry references. Both report unreachable repos under
  `unreachable` (state untouched) and are `ok:false` + exit 1
  (`unreachable_repos`) only when NO repo could be evaluated/scanned.
- New error kinds: `unknown_group`, `partial_save`,
  `partial_restore`, `unreachable_repos`.

### The partial-failure transport problem

`save`/`restore-group` report per-repo outcomes individually and are
honest about partial success: the full report is printed on **stdout**,
a `{kind:"partial_save"|"partial_restore"}` summary goes to **stderr**,
and the exit code is 1 (`ok:true` only when every repo succeeded).
`gc`/`prune` use the same shape when nothing is evaluable. The bridge's
`plugin_call` previously surfaced non-zero exits as a thrown
`HerdrError` parsed from stderr — silently dropping the per-repo
report on stdout. plugin_call returns exactly one document, so the
report cannot ride a second channel.

## Decision

1. **Pin**: herdr-t3 consumes `herdr-plugins.checkpoints/v1` as
   implemented at `rebuildup/herdr-plugins@ae4f214` (release-0-4-0,
   plugin version 0.4.0), superseding the `55df8d0a` pin. Older plugin
   builds simply omit `save`/`restore-group`/`gc`/`prune` from
   `capability.commands`; every new affordance is capability-gated.
2. **Partial reports cross the bridge as documents, not errors**:
   `outcomeToJson` (server/plugins.ts) now detects the partial
   convention — non-zero exit + a contract error object on stderr +
   a JSON document on stdout that itself reports `ok:false` — and
   returns the stdout report as the result document with the stderr
   `error` object attached under `error` (bounded via
   `boundErrorValue`). Hard failures emit no stdout document and still
   throw; a stdout doc that does not self-report `ok:false` is treated
   as a failure, never a success. This is generic across plugin
   contracts: any plugin using the same stdout-report + stderr-summary
   convention benefits, and no contract-specific kinds are hard-coded
   in the bridge.
3. **Honest per-repo rendering**: `save`/`restore-group`/`gc`/`prune`
   parsers keep `ok:false` payloads as first-class results
   (`CheckpointSaveResult`, `CheckpointRestoreGroupResult`,
   `CheckpointGcResult`, `CheckpointPruneResult`) with the attached
   `error` (`partial_save`/`partial_restore`/`unreachable_repos`)
   preserved. Per-repo `ok:false` entries render individually with
   their plugin error kind — never collapsed into a generic failure.
   The new kinds are also registered in `CHECKPOINTS_ERROR_KINDS` so
   older bridges that throw them classify distinctly.
4. **UI surfaces**: `save` gets a repo-set selector (live discovery /
   focused pane / explicit repo list via one-path-per-line textarea)
   with `skipped_panes` shown; `list --group` filter + `group_id`
   badges; `restore-group` reuses restore semantics per repo (confirm,
   per-repo pre_restore/isolation/panes, `--force` only as a labelled
   retry when a member failed `shared_worktree`/`session_unreachable`,
   re-running the whole group as upstream does); `gc`/`prune` require
   a fresh dry-run preview of identical parameters before the execute
   button enables — parameter edits invalidate the preview.
5. **Retention is plugin-owned**: gc/prune policy, eviction and orphan
   detection all run plugin-side; the client only previews and
   forwards. Unreachable repos are displayed as skipped, never as
   deleted.

## Consequences

- Hosts on `55df8d0a` keep working unchanged (no group/retention
  commands advertised → affordances hidden); pc-setup hosts need the
  re-pinned plugin build for the new surface.
- The bridge now returns a document for the partial convention on ANY
  plugin contract; callers that assumed non-zero exit always throws
  must tolerate `ok:false` documents — the checkpoints parsers do, and
  other contract parsers already check `command`/`ok` fields.
- `gc`/`prune` are destructive; the mandatory dry-run gate is a UI
  rule, not a contract rule — CLI users can still run them directly.
- Remaining upstream non-goals: no per-turn (per-message)
  auto-capture, no private object store/quarantine, no submodule
  worktree capture/restore.
