# ADR-0014: Projects/Scripts surface — projects-v1 contract pin and scope

- Status: Accepted
- Date: 2026-11-26
- Extends: ADR-0011 (plugin consumption boundary); same pinning rule as
  ADR-0012.
- Program: issue #188; tickets #252 (registry UI), #253 (scripts UI);
  groundwork #251.

## Context

`rebuildup/herdr-plugins` release-0-3-0 (`c8460283`) publishes
`herdr-plugins.projects/v1` (`docs/contracts/projects-v1.md`, plugin
`rebuildup.projects` v0.1.0): a host-global project registry (multi-repo
grouping, pin/archive, settings overrides) plus project-defined scripts
(`t3.json` resolution, `scripts run|stop|results|logs`). Upstream Issues
#48–#53 are closed; #26/#3 remain open as parents; #60 tracks the
unimplemented auto triggers.

Facts that shape the client integration:

- The registry is **host-global** (plugin state dir, not per-session).
  `list`/`show`/`capability` work without a live herdr session;
  `discover` and all `scripts *` commands need one (session snapshot /
  pane execution).
- `capability.commands` advertises only top-level words
  (`list`, `settings`, `scripts`, `repos`, …); subcommands such as
  `settings get` or `scripts run` are argv arguments, and
  `mutation_commands` entries carry the subcommand (`"settings set"`,
  `"scripts run"`). Client gating must therefore map
  command+subcommand pairs, not assume one word per operation.
- `scripts run` makes the plugin create a dedicated herdr workspace and
  pane, inject the command once, and await a sentinel marker for the
  exit code. Results are `running|success|failed|stopped|unknown` —
  `unknown` is an honest "pane vanished", never fabricated success.
- Auto triggers (`runOnWorktreeCreate`/`runOnSettle`/`stopOnSettle`) are
  resolved and listed but have **no execution mapping** upstream
  (herdr-plugins#60). The client must not imply they fire.

## Decision

1. **Pin**: herdr-t3 consumes `herdr-plugins.projects/v1` as implemented
   at `rebuildup/herdr-plugins@c8460283` (release-0-3-0). The formal
   release tag is fixed at release-candidate time; the pin, not a moving
   branch, is the adoption point (ADR-0011/0012 rule).
2. **Two independent surfaces**: the registry (#252) and scripts (#253)
   ship as separate dialogs behind separate menu entries, each with its
   own store module (`src/shell/projects.ts` /
   `src/shell/projectScripts.ts`) so the tickets stay file-disjoint and
   parallel-safe. Both go through `plugin_call` only — no plugin state
   file reads, no direct `t3.json` parsing, no Electron dependencies.
3. **Honest gating**: every operation checks the host's
   `capability.commands` (top-level word) and, for mutations,
   `mutation_commands` (command + subcommand pair). `repo_ambiguous`,
   `unknown_script`, `run_not_found` etc. surface with their plugin
   `error.kind`, never collapsed into generic failures.
4. **Scripts are view/operate, not trigger**: the UI lists definitions
   (including `runOn*` flags as inert metadata), runs/stops explicitly,
   and shows `results`/`logs`. Auto-trigger fields are displayed as
   "not wired" until herdr-plugins#60 lands; the client never fakes
   trigger state.
5. **Checkpoints stay out of this ADR**: the checkpoints capability
   (herdr-plugins#4) has no published contract at `c8460283`; #221
   narrows to that remainder and stays blocked.

## Consequences

- pc-setup#239 owns making `rebuildup.projects` installable per host
  (`git` + `bun` prerequisites; herdr session for discover/scripts).
- New surfaces register in `docs/migration/capabilities.json`
  (`projects.registry`, `projects.scripts`) at `contract-defined`;
  implementation tickets advance stage with evidence.
- A host without the plugin (or an older build) yields
  capability-gated UI — "not supported by this plugin version" or the
  boundary unavailability reason — never a fake empty registry.
