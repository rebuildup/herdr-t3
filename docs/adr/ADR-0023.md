# ADR-0023: plugin exec env scrub — no ambient GIT_* targeting vars

- Status: Accepted
- Date: 2026-11-26
- Amends: ADR-0022 (plugin exec env scrub).
- Program: issue #188; ticket #280. Upstream:
  rebuildup/herdr-plugins#96 (OPEN — upstream fix is defense in depth
  on our side; we scrub regardless of upstream landing it).

## Context

ADR-0022 scrubbed ambient `HERDR_*` targeting vars so plugin CLIs
cannot be redirected to a foreign herdr session/socket/pane. The same
defect class exists for git: upstream `packages/git-core`
(`runGit`/`runGitBounded`, release-0-4-0) and
`plugins/git/src/git.ts` (diff streaming) spawn `git` with
`...process.env` verbatim, pinning only `GIT_TERMINAL_PROMPT=0`,
`GIT_OPTIONAL_LOCKS=0` and `LC_ALL=C`. A herdr-t3 server launched
inside a herdr pane or plugin runtime inherits the ambient
environment, so `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`/
`GIT_OBJECT_DIRECTORY`/`GIT_CONFIG_*`/`GIT_SSH*` present there would
silently redirect plugin git operations — checkpoints capture writes
objects into the wrong object store, restore/checkout touch a foreign
worktree, and config/env-config injection can rewrite `core.*`
targeting. Upstream herdr-plugins#96 proposes unsetting the vars in
git-core; until that lands (and for plugin revisions already
installed), the bridge must not rely on it.

## Decision

1. **`PLUGIN_ENV_SCRUB` gains the GIT_* targeting set.** Same list,
   same removal semantics, applied identically to `plugin_list`
   discovery, `capability` probes and `plugin_call` on local and SSH
   hosts — the plugin CLI's environment is what every upstream `git`
   spawn inherits.
2. **Included vars** (repo/index/object-store targeting):
   `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`,
   `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`,
   `GIT_COMMON_DIR`, `GIT_NAMESPACE`, `GIT_PREFIX`,
   `GIT_CEILING_DIRECTORIES`, `GIT_DISCOVERY_ACROSS_FILESYSTEM`.
   (Config targeting/injection): `GIT_CONFIG`, `GIT_CONFIG_GLOBAL`,
   `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`,
   `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`. (Transport/subprocess
   lookup): `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`,
   `GIT_PROXY_COMMAND`, `GIT_EXEC_PATH`.
3. **Indexed config family handled without prefix matching.**
   `GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>` cannot be enumerated by
   a static list, but git only reads them when `GIT_CONFIG_COUNT` is
   set — scrubbing the count neutralizes every index. No prefix/glob
   support was added to `envRemove` (POSIX `unset` does not glob and
   PowerShell `$env:` needs literal names); this is the minimal
   correct approach. `GIT_CONFIG_PARAMETERS` is scrubbed separately
   because git parses it unconditionally.
4. **Deliberate exclusions.** `GIT_PAGER`, `GIT_EDITOR`,
   `GIT_SEQUENCE_EDITOR`, `GIT_MERGE_AUTOEDIT` select editor/pager
   programs rather than redirect repo/config/transport targeting, and
   interactive prompting is already pinned off upstream
   (`GIT_TERMINAL_PROMPT=0`). `GIT_SSH_VARIANT` only selects ssh output
   parsing; `GIT_AUTHOR_*`/`GIT_COMMITTER_*` are commit identity;
   `GIT_TRACE*` are diagnostics; `GIT_TEMPLATE_DIR` affects `git init`
   only; `GIT_QUARANTINE_PATH`/`GIT_SHALLOW_FILE`/
   `GIT_REPLACE_REF_BASE` are git-internal state vars. None can point
   an operation at a different repository.

## Consequences

- No ambient `GIT_*` var can redirect plugin git operations to a
  foreign repository, object store, index, config file or transport;
  plugin CLIs fall back to cwd-based repo discovery and the user's
  normal config files — identical to a clean shell.
- When upstream herdr-plugins#96 lands its own git-core scrub, the
  two layers are complementary (bridge env removal + in-plugin spawn
  hygiene); neither depends on the other.
- Residual: a plugin that *intentionally* needs a non-default
  `GIT_*` (none in the published contracts) could not receive it
  through ambient env; contract args remain the supported channel.
- Contract tests pin the extended list on every exec kind and on the
  real local spawn (`server/plugins.test.ts`,
  `server/machines.test.ts`).
