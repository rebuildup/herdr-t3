# ADR-0010: Pane size authority stays with herdr; attach does not negotiate size

- Status: Accepted
- Date: 2026-11-25
- Relates: ADR-0007 (libghostty-vt terminal), issue #214, upstream
  herdrdev/herdr#6188

## Context

herdr's private client protocol gives a writable `AttachTerminal` client
full control of the attached pane's PTY size: on attach and on every client
`Resize`, the server calls `runtime.resize(rows, cols)` and records the
terminal in `direct_attach_resize_locks`, which blocks layout-driven resizes
from other clients until detach (herdr `src/server/headless.rs` @ `e8d7d97`,
protocol 22). This is correct for a client that *is* the terminal — the TUI —
but herdr-t3 is a GUI viewer that attaches to panes to render them with its
own cell grid.

Consequence observed by the maintainer: while herdr-t3 has a pane attached,
that pane's size is fixed at the GUI's cols/rows and the herdr TUI can no
longer resize it — "herdr-t3 のせいで他の herdr から見てもサイズが固定
されてしまっていて使いづらい" (issue #214).

Protocol facts that bound the solution space:

- `ObserveTerminal` streams the pane without touching size or input, but
  `ClientInput` is routed only for `TerminalAttach` mode — observe clients
  cannot type.
- `TerminalFrame` already carries `width`/`height`, so a client could in
  principle render whatever grid the server reports.
- There is no v22 message that attaches writable input without size
  authority; `TerminalHello`/`AttachTerminal`/`Resize` are the only sizing
  surface.

## Decision

1. herdr-t3 does **not** attempt to decouple pane size from the attach
   stream client-side. The attach stream remains the truth (AGENTS.md §3);
   the engine grid follows the GUI's measured cell size and
   `terminal_resize` reports it, exactly as today.
2. The size-authority conflict is an upstream protocol gap, tracked as
   herdrdev/herdr#6188 (writable attach without resize authority). herdr-t3
   prepares no fork or shim; if upstream ships an option, `client-link.ts`
   and `bridge-core.ts` gain an attach flag and this ADR is revisited.
3. Interim mitigation is limited to what the client already does: only panes
   in the active tab are mounted (and therefore attached), and detach
   releases the lock so sizes return to layout control. Issue #213's
   resize throttling reduces how often the GUI *changes* a locked pane's
   size, but cannot remove the lock itself.

## Consequences

- While a workspace is open in herdr-t3, its panes are sized by the GUI and
  the TUI cannot resize them; closing/detaching restores TUI control. This
  is documented behavior, not a bug to be patched around.
- Any future "view without owning size" mode must come from upstream; the
  client will adopt it behind the existing attach options rather than
  inventing a parallel transport.

## Amendment (issue #571, program #568)

Upstream herdrdev/herdr#6188 was closed as a feature request and redirected
to Ideas discussions; no attach/resize protocol change has shipped since
the v22 pin (`e8d7d97`). Interim non-interference landed anyway using what
v22 already provides: only the focused pane of the visible tab holds
writable `AttachTerminal`; every other mounted pane streams through
read-only `ObserveTerminal`, which takes no resize lock and cannot carry
input. Mode flips are negotiated on the live bridge slot via
`subscribe_terminal { writable }` (see
`docs/migration/contracts/terminal-noninterference.md` for the full
contract and the upstream capability spec this program canonizes). The
size-authority decision above is unchanged: writable attach still owns
size; observe is the non-interfering view.

## Amendment (issue #584, program #568)

GUI pane focus is further separated from the inter-client operator role:
writable attach is granted only by real input intent (click, keystroke,
mouse press, paste, link activation) and released when herdr focus moves
to another pane — viewing and history scrolling never hold the resize
lock. Contract v2 in
`docs/migration/contracts/terminal-noninterference.md`.
