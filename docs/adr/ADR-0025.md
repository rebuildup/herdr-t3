# ADR-0025: Transitional Rust consumer — wasm-in-runtime for small-data capabilities, no transitional consumer for per-frame paths

- Status: Accepted
- Date: 2026-11-26
- Program: issue #233; ticket #314. Relates to ADR-0013 §3 (one-way
  dependency; the current app may host Rust components during
  transition) and ADR-0007 (terminal engine).
- Scope: how `rust-implemented` capabilities reach the shipping product
  before the GPUI host exists, and the measured cost of each candidate
  connection.

## Context

The product-path audit (roadmap, issue #233) found all six
`rust-implemented` capabilities — `protocol.codec`, `agent.projection`,
`terminal.engine`, `terminal.scene`, `terminal.input`,
`terminal.surface` — serve only the differential/ui harness adapters.
No shipping code path calls the Rust crates, so `switched` and old
implementation removal cannot proceed.

ADR-0013 §3 permits the current app to host Rust components during the
transition but fixes only the dependency direction. It does not choose
the mechanism. The mechanism is disposable by design: whatever connects
Rust to the product today must not become a permanent architecture
constraint on the GPUI end-state, and per-frame paths must not pay
serialization copies that GPUI will not need.

Candidate mechanisms evaluated:

- **(a) napi-rs native module** in Electron main / Bun server, reached
  from the sandboxed renderer (`sandbox: true`, `contextIsolation:
  true`) only through IPC structured clone.
- **(b) Rust sidecar process** speaking JSON-lines frames over stdio or
  a local socket.
- **(c) wasm32 module** loaded directly by the consuming runtime
  (precedent: `shared/ghostty/ghostty-vt.wasm` already loads in the
  renderer; Bun runs wasm too).

## Measured evidence (2026-11-26, Apple Silicon, debug builds)

| Cost | wasm (bun/JSC) | sidecar (stdio) | napi+IPC (est.) |
|---|---|---|---|
| Per-call boundary | ~15 ns bare export | ~50–200 µs pipe+parse (persistent); ~18 ms spawn-per-call | ~100 ns FFI + ~5–50 µs IPC |
| Payload copy | op payload only, in linear memory | full JSON serialize+parse per call | structured-clone per call |
| Bulk data (60 KB scan) | ~112 µs, zero copy | ~MB/s JSON at 60 fps ≈ 6 MB/s for frame paths | same copy via IPC |
| Instantiation | ~19 ms once, data artifact (no codesign impact) | process lifecycle per capability | native binary per platform, codesign/notarize |
| Rust compute (reference) | projections ~2 µs/op; input ops sub-µs | same | same |

serde_json on a ~200 B op payload: ~430 ns parse (bun), comparable in
Rust. Compute is never the bottleneck; transport and copies decide.

## Decision

1. **Small-data, call-shaped capabilities consume Rust via wasm32
   modules inside the consuming runtime.** `terminal.input`,
   `agent.projection`, `protocol.codec` (guard/validate paths), and
   `ui.goto-picker`-class view-models qualify: payloads are hundreds of
   bytes, call rates are per-keystroke/per-snapshot, and the wasm
   boundary costs ~15 ns + payload serialization — orders of magnitude
   below any perceptible threshold and below the TS implementation's own
   cost.
2. **Per-frame capabilities get no transitional consumer.**
   `terminal.engine`, `terminal.scene`, and `terminal.surface` move
   frame-sized data every paint. Any IPC/sidecar/wasm-marshal path
   inserts a mandatory serialize+copy of kilobytes-to-megabytes per
   frame that the GPUI end-state will not have. Their `switched` step is
   the GPUI surface itself (boundary 4→5 path, already proven by
   `ui-test-host` + `terminal-surface`/`terminal-render` crates); the
   registry records removal of the TS implementation as part of that
   cutover, not via a disposable bridge.
3. **Sidecar processes are rejected** for capability consumption: the
   persistent-process variant still pays pipe latency + full JSON
   round-trips per call, and the spawn-per-call variant measured ~18 ms
   — both strictly worse than wasm for every payload shape, while
   adding a process lifecycle, socket/stdio failure modes, and a second
   deployment artifact.
4. **napi is rejected for the renderer path** (sandboxed
   `webPreferences` cannot load native modules; reaching main via IPC
   reintroduces the structured-clone copy of option (a) with none of
   wasm's in-memory advantage). It remains a fallback only if a future
   capability proves un-wasm-able (e.g. needs the native
   libghostty-vt); `terminal-core` is exactly that case and is covered
   by decision 2 instead.
5. **wasm artifacts are build outputs vendored like
   `ghostty-vt.wasm`** — data files, not native code, so they carry no
   codesign/notarization delta on either OS. Each consuming runtime
   loads the module for its platform target; the crate set stays
   runtime-agnostic per migration-policy §5.
6. **Removability is explicit.** Every wasm consumer added under this
   ADR is registered against its capability's `switched`/`removed`
   stage: when the GPUI host consumes the crate natively, the wasm
   artifact and loader are deleted with the TypeScript implementation.
   No product code may depend on the wasm boundary's shape (opaque
   slots, linear-memory indexing) — only on the crate's typed API.

## Consequences

- `protocol.codec`, `agent.projection`, `terminal.input` (and later
  `ui.*` view-models) get a product-path switch ticket per capability
  (#315/#316/#319 and boundary-5 slices), each delivering: wasm build
  wiring in CI, a thin loader in the consuming runtime, the existing
  differential scenarios replayed through the wasm artifact as
  equivalence evidence, and registry stage advancement.
- `terminal.engine`/`terminal.scene`/`terminal.surface` switch tickets
  (#317/#318/#320) are re-scoped: their equivalence evidence is the
  existing crate + `ui-test-host` conformance, and their product
  replacement lands with the GPUI surface — no interim consumer.
- The Electron→Rust connection therefore cannot calcify: wasm modules
  are per-capability, per-runtime, and deleted at `removed`; nothing in
  the end-state architecture references them.

## Verification

- Measurements above are reproducible: the wasm probe is a trivial
  `#[no_mangle]` cdylib compiled with
  `rustc --target wasm32-unknown-unknown -O` and instantiated from bun;
  `cargo build -p terminal-input --target wasm32-unknown-unknown`
  already succeeds unmodified (serde_json included), confirming the
  crate set is wasm-clean today.
- Per-capability switch tickets must re-run the same comparison if the
  payload shape changes (e.g. a projection op growing past ~100 KB
  would re-open the sidecar/napi question with fresh numbers).
