# ADR-0032: Controls surface — controls-v1 contract pin @d23205af and gated mutation adoption

- Status: Accepted
- Date: 2026-12-09
- Program: issue #188 (T3 parity); ticket #450. Plugin-surface
  consumption of `rebuildup.controls`; same ADR-0011 `plugin_call`
  boundary as ADR-0012/0014/0016/0026/0027/0028/0030.
- Pin: `rebuildup/herdr-plugins@d23205af0cd2ff7dba25f72e1f3b872762a108ee`
  = tag `v0.9.0`, contract `herdr-plugins.controls/v1` (**v1 stable**
  since herdr-plugins v0.6.0 / plugin v0.6.0). Upstream spec:
  `herdr-plugins/docs/contracts/controls-v1.md`.

## Context

`rebuildup.controls` is the agent operation core: provider
slash-command passthrough (`agent.prompt`), status wait
(`agent.wait`), PTY-level key injection (`agent.send_keys`), scrollback
read (`agent.read`), rename (`agent.rename`), and agent launch
(`agent.start`) with per-provider launch-option argv mapping — all
over herdr's `agent.*` socket API, every agent-target command guarded
by `--expect-pane`/`--expect-state-seq`/`--expect-agent-session` that
aborts `stale_generation` before mutation. The capability document
additionally carries a per-provider launch support table
(`model`/`reasoning`/`permission_modes`/`resume`), an advisory
fragile `commands.known` slash-command list, and a `dialogs` verdict
table (all `unsupported`/`pty_level` in v1).

Unlike handoffs/artifacts this contract is primarily **mutating**:
`mutation_commands` advertises `send`/`command`/`interrupt`/`rename`/
`start`; `wait`/`read`/`capability` are non-mutating. Several of the
plugin's operations duplicate capabilities herdr already exposes to
the bridge, so a naive port would reimplement herdr's built-in agent
operations — the issue's explicit non-goal.

## Decision

1. Consume `capability`, `command`, `wait`, `interrupt`, `start` only.
   The local `CONTROLS_MUTATION_COMMANDS` allowlist is exactly
   `command`/`interrupt`/`start`, intersected with the advertised
   `mutation_commands` and flat `commands` list
   (`controlsSupportsMutation`, fail-closed on probe states). `send`
   and `rename` are contract mutations deliberately left out of the
   allowlist: they are the same upstream calls the bridge already
   exposes (`agent.prompt` via the prompt dialog, `agent.rename` RPC),
   and the plugin adds only the identity echo/guards this client emits
   anyway. `read` duplicates `agent.read` pane diagnostics; conversation
   history belongs to `herdr-plugins.conversations`. `--arg`/
   `--unsafe-args` raw argv passthrough stays plugin-CLI-only.
2. `src/shell/controls.ts` mirrors the `handoffs.ts`/`automations.ts`
   store shape: per-machine capability state
   (`probing|ready|unavailable|error`), defensive `*FromDoc` parsers
   rejecting foreign contracts and malformed documents, the shared
   unavailable-reason taxonomy (plugin-side kinds stay `error` with
   verbatim detail), a TTL-cached capability probe requiring the
   consumed command set in `commands`, and refresh on snapshot pushes
   (800ms debounce, 15s/probe cap — the #422 amplification guard),
   machine-status transitions, and machine-list changes via
   `initControls()`. There is no eager data read: agents come from the
   live snapshot; every operation is an explicit user action.
3. Identity guards are automatic, never user-typed:
   `controlsExpectFromAgent` derives `--expect-pane` (always),
   `--expect-state-seq` and `--expect-agent-session` (when herdr
   reports them) from the selected snapshot agent record. A stale
   generation aborts plugin-side before any mutating `agent.*` call;
   `stale_generation` renders as verbatim error detail. `start` takes
   a pane id (no prior generation), so guards do not apply.
4. Provider launch options are gated by the capability's own verdicts:
   `model`/`reasoning` booleans, `permission_modes` keys
   (`supervised|auto-accept-edits|auto|full-access`), and
   `resume != "unsupported"` (with the contract's `resume` detail
   string shown verbatim). Unsupported options are hidden, never
   defaulted — `unsupported_launch_option` stays an upstream error if
   ever reached. `--resume`/`--resume-from` are mutually exclusive
   client-side too; `--timeout-ms` is emitted only inside the contract
   bound `(3000, 300000]`; `--wait-timeout-ms` has no documented bound
   and passes through.
5. Slash commands: the GUI normalizes input to the contract regex
   `/[A-Za-z][A-Za-z0-9_-]*/` and offers the provider's advisory
   `commands.known` as clickable chips — explicitly labeled fragile/
   unverified per the contract; `known_command` is a result hint, never
   a gate. `command` submits via `agent.prompt` passthrough, so a
   `blocked` agent surfaces `requires_interactive_input`; the surface
   warns before submit but never fabricates success.
6. Every mutation runs through an explicit confirmation `Dialog`;
   `wait` (non-mutating per contract) needs none but is labeled as a
   status observation. Result documents echo `identity`,
   `passthrough`/`pty_level`/`fragile`/`waited`/`launch.applied`
   verbatim — `interrupt` is labeled "PTY-level key injection, not a
   structured interrupt" because that is what the contract says it is.
7. `src/components/ControlsSurface.tsx` renders the surface with T3
   Code primitives only: agent picker (snapshot agents + free-form
   target), per-provider capability panel (launch table, command
   chips, dialogs verdicts, upstream gaps), operation sections, and
   confirmation dialogs. Wiring follows the established right-panel
   pattern: `rightPanelStore` union + `isSurface`, `RightPanel`
   icons/titles/content/add-actions, `CommandMenu`/`WorkspaceHeader`
   entries, `initControls()` in `App.tsx`.

## Consequences

- Agent control becomes reachable from the GUI through the plugin
  contract with generation-safe mutations; herdr's built-in agent ops
  are not reimplemented — the consumed set is exactly the
  contract-specific value-add (provider launch table, slash-command
  passthrough with advisory lists, guarded mutations).
- `send`/`rename`/`read` staying bridge-owned means two paths to the
  same upstream calls exist; the contract doc records the decision so
  a future ticket can revisit (e.g. if plugin-side identity guards on
  `send` prove valuable).
- The advisory `commands.known` lists are fragile by contract — the UI
  presents them as hints and always allows a custom name.
- Mutation risk is bounded by capability gating + confirmation +
  expect-guards; `interrupt` remains PTY-level (no structured
  interrupt API upstream — recorded in `upstream_gaps`).
- Contract pin is recorded here and in
  `docs/migration/contracts/plugin-controls.md` +
  `docs/migration/capabilities.json`; a future contract revision
  re-pins via a new ADR per the established rule.
