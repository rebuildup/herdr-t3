# ADR-0013: GPUI staged migration — contract-first foundation and Electron removal gates

- Status: Accepted
- Date: 2026-11-25
- Program: issue #233 (parent), tickets #234–#241 (M01–M07)
- Amends: none; extends ADR-0002 (architecture), ADR-0003/0008 (UI stack
  and shell), ADR-0007 (terminal engine), ADR-0011 (plugin boundary)
- Canonical policy: `docs/design/migration-policy.md`

## Context

herdr-t3 is an Electron + TypeScript application: `desktop/main.ts`
hosts the herdr bridge in-process, `desktop/preload.cjs` exposes the
`shared/protocol.ts` frame contract over IPC, `src/` renders the T3 Code
shell in React, and `shared/ghostty/` + `src/lib/ghostty/` run the
libghostty-vt terminal. The long-term goal is to replace the renderer and
shell with Rust/GPUI and eventually remove Electron and the Node/Bun
runtime dependencies entirely.

Issue #233 fixes the program invariants: contract-first and
verification-first migration, no capability regression, one state owner
per domain, no reverse dependency from the Rust core into
Electron/Node/Bun, per-capability staged cutover with pre-defined removal
conditions, and measured (not assumed) performance. Product porting must
not start before the readiness gate defined by this program is met.

## Decision

1. **Migration proceeds capability-by-capability, contract first.** The
   externally observable contract of each boundary is fixed and verified
   against the current implementation *before* any Rust/GPUI code
   replaces it. The current implementation's behavior is the differential
   oracle; the normative specification stays separate so existing bugs
   are filed as issues rather than codified.
2. **Boundaries are the migration units.** The candidate boundaries —
   protocol/state projection, terminal engine/frame pipeline,
   streaming/render scheduling, pane/UI composition, settings/persistence,
   native shell/OS integration, distribution — are enumerated with their
   dependency direction and state ownership in
   `docs/design/migration-policy.md`. A capability may only be ported
   when its contract, conformance evidence, and rollback path exist.
3. **One-way dependency.** The Rust core may depend on shared
   specifications and herdr/plugin contracts. It must never depend on
   Electron, Node, Bun, or the current TypeScript implementation. The
   current app may host Rust components during transition; the reverse
   direction is forbidden. Temporary dual implementations are allowed
   only inside a capability's migration window and must carry a removal
   condition in the capability registry.
4. **State ownership does not move.** herdr owns ptys, scrollback and
   agent state; plugins own feature state (ADR-0011); the app owns UI
   state and user settings. The Rust/GPUI side inherits exactly the
   ownership the TypeScript side had — it does not absorb herdr or plugin
   state, and no second store may appear during migration.
5. **Terminal semantics are the spec, not the engine.** ADR-0007's
   libghostty-vt behavior and `docs/design/terminal-io.md`'s byte-level
   input/output contract are the normative terminal contract. Whether the
   Rust side keeps WASM libghostty-vt, embeds a native terminal core, or
   splits engine/frame responsibilities is decided per-boundary by
   evidence (differential harness #237, performance baseline #240), not
   by assumption.
6. **T3 design semantics survive; implementation does not.** Tokens,
   primitives' behavior, density and interaction rules from
   `docs/design/` remain canonical. React/Tailwind/Base UI are the
   current implementation of those semantics, not the contract — the UI
   conformance harness (#238) asserts semantics, not DOM structure.
7. **GPUI is the target UI, with evidence gates.** GPUI's upstream
   revision, license, platform coverage (macOS and Windows 11, including
   IME, clipboard, accessibility, windowing and distribution) are
   evaluated by a minimal non-product spike before any product porting.
   If GPUI cannot satisfy a required OS capability, that gate stays
   blocked and is reported — it is not waived.
8. **Release train.** Preparation tickets (#234–#241) target the current
   release train `release-0-6-0` because it is the only active integration
   line and is not frozen. Tickets that do not land before its freeze
   retarget to the next train; `release-* -> main` keeps its explicit
   authorization boundary. This program does not freeze or extend the
   #188 parity scope.
9. **Verification is tiered per ADR-0036 / profile.yaml.** Ticket PRs run
   static + local + contract + targeted-diff checks. The full E2E, both-OS
   real-machine, performance, distribution-artifact and visual review
   suite aggregates on the release candidate at the same frozen SHA.
   Unrunnable or skipped verification is never recorded as pass.

## Consequences

- The migration foundation produces ADR/policy (#234), a machine-readable
  capability registry and behavioral contracts (#235), differential and UI
  harnesses (#237, #238), persistence/OS compatibility contracts (#239),
  a reproducible performance baseline (#240), and CI/readiness/roadmap
  enforcement (#241). None of these port product features.
- `quality/profile.yaml` gains migration-specific change-risk entries as
  the harnesses land; `scripts/ci.sh` and `.github/workflows/ci.yml` are
  updated to match (ticket #241).
- New long-lived decisions (exact GPUI pin, Rust workspace layout,
  terminal-engine choice, cutover order) are recorded as ADRs when the
  evidence exists — this ADR fixes the gates, not the answers.

## Amendment (issue #587, program #568 → #233)

The terminal non-interference capability set canonized in
`docs/migration/contracts/terminal-noninterference.md` v2 (specs C1–C5,
hoxay tickets H-NI-1..6) is a **contract requirement for the B2 bridge
and B4 terminal boundaries** under this program, not optional future
work:

- B2 (`crates/herdr-bridge`) must implement the attach-mode state
  machine, per-client scroll offsets, and demand-driven history paging
  behind the `terminal-noninterference` contract — degrading to the
  observe/promotion interim against herdr protocol v22, adopting the
  new wire variants when `Welcome.version` advertises them.
- B4 (`crates/terminal-core` / `crates/terminal-render`) must render
  per-client viewport offsets and history pages stable across appends
  without rebuilding attached panes from `pane.read` (AGENTS.md §3).
- The native-backend half (H-NI-5: page store, per-(terminal,client)
  viewport state, mode/grant authority) is a #233 roadmap item gated on
  the same readiness evidence as every other boundary — it is listed in
  `docs/migration/capabilities.json` scope via the contract, not started
  by this amendment.

No product porting is authorized by this amendment; it records that the
#233 capability registry must carry these requirements so cutover does
not silently drop non-interference semantics the Electron client already
delivers.

## Unresolved (evidence required, not decided here)

- Exact GPUI dependency source and pinned revision (crates.io `gpui`
  0.2.2 predates the platform split; current standalone usage tracks the
  Zed repository — see migration-policy.md §GPUI evaluation).
- Whether libghostty-vt WASM remains the terminal core on the Rust side.
- Rust workspace layout and CI runner/toolchain provisioning.
- Per-capability cutover order — fixed by the readiness data in #241,
  not upfront.
