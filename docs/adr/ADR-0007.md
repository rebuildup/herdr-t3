# ADR-0007: Terminal — libghostty-vt engine replaces xterm.js

- Status: Accepted
- Date: 2026-11-23
- Supersedes: none (revises the renderer choice inside ADR-0002/ADR-0005)

## Context

The pane terminal was xterm.js (`@xterm/xterm` + fit/web-links/unicode
graphemes addons). Ovis has since proven a different stack in production:
`libghostty-vt` compiled to WebAssembly — a host-free terminal core
(`shared/ghostty/engine.ts` + `ghostty-vt.wasm`, MIT) plus a per-pane
emulator layer (`tui/emulator/`). It provides emulation, scrollback,
key/mouse/paste encoders, terminal-query replies, selection text
extraction, search and Kitty graphics — everything a terminal surface
needs, without xterm.js's DOM/canvas renderer and its private-API
coupling.

The next release (0.2.0) integrates that proven implementation into
herdr-t3 (Issue #51). Keeping xterm.js as a fallback would leave two
emulators, two input paths and two selection models to keep consistent —
the "暫定アダプター" the integration explicitly rules out.

## Decision

- **libghostty-vt is the only terminal emulator.** `@xterm/*` dependencies
  and all xterm imports are removed. There is no xterm fallback path.
- **Source of truth for the port** is the pinned Ovis commit in
  `docs/upstream.md` (`e16802a2f`): `shared/ghostty/engine.ts`,
  `shared/ghostty/ghostty-vt.wasm`, and the screen emulator layer
  (`tui/emulator/{index,ghostty,graphics}.ts`), adapted to this
  repository's layout. THIRD_PARTY_NOTICES records the reuse.
- **One emulator per pane.** Each `PaneTerminal` owns a `GhosttyEmulator`
  on its own WASM instance — no shared module memory, so one pane's trap
  cannot take down another's. The browser's shared-module loader from
  Ovis (`src/lib/ghostty/vt.ts`) is not ported.
- **The attach stream stays the truth.** Output bytes feed
  `emulator.write()`; on bridge reconnect the server's subscribe replay
  redraws the screen. The emulator is never rebuilt from `pane.read`.
- **Input is encoded by the engine.** DOM `KeyboardEvent`/`PointerEvent`
  are translated to `EngineKey`/`EngineMouse`/paste text and encoded by
  libghostty's own encoders, which follow the modes the program set
  (Kitty keyboard flags, mouse protocol/format, bracketed paste,
  win32-input-mode). Terminal query replies (`onReply`), bells and OSC 52
  clipboard writes surface through `EngineEvents`.
- **Wire contract carries bytes.** `terminal_input.data` becomes
  base64-encoded bytes (same convention as `terminal_data`), because
  encoded input and emulator replies are arbitrary bytes, not necessarily
  valid UTF-8. The frame shape is unchanged otherwise; the dev WebSocket
  and the desktop IPC share the same contract.
- **Rendering is a DOM row surface.** `frame()`/`frameAll()` runs are
  drawn as styled row elements; the cursor, selection highlight, scroll
  position and Kitty images are positioned overlays. Selection, word/line
  select, scrollback (`scrollFromBottom`, `history`) and `textOf` come
  from the engine — no second text model exists.
- **Scrollback is engine-owned** (`TERMINAL_HISTORY_LINES` equivalent,
  2000 lines, matching Ovis). Wheel/trackpad scroll moves the engine
  viewport; output while scrolled does not yank the view.
- **Theme flows one way.** T3 semantic tokens drive the chrome; terminal
  colors come from `engine.setColors()` fed by the Appearance mode —
  Ghostty sync palette (Issue #35) when active, otherwise the T3
  terminal tokens. Changes apply live without restart.
- **Grapheme clustering uses `widths: "core"`** — libghostty's own
  clustering — since the emulator, not xterm, defines cell metrics.
- **Kitty graphics are enabled** (`images` storage budget as in Ovis),
  with `GraphicsQueries`-style refusal only where the engine cannot
  answer.

## Consequences

- `PaneTerminal` is rewritten around the emulator; `App.tsx`'s pane
  mounting, machine namespacing and focus RPCs are unchanged — the
  terminal view owns DOM focus and keyboard input for the focused pane.
- The wire `terminal_input` semantic change touches `shared/protocol.ts`,
  `server/bridge-core.ts` and every sender; it is an internal contract
  versioned with the app, not a public API.
- IME composition commits are sent as UTF-8 text bytes (equivalent to
  typing); they are not paste-bracketed.
- Verification must cover what xterm used to hide: key encoding across
  keyboard layouts and modifier combos, mouse reporting modes, scrollback
  correctness, and per-pane isolation.
