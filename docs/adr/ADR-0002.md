# ADR-0002: Architecture — dedicated herdr bridge + T3 design system

- Status: Accepted
- Date: 2026-11-22

## Context

Two candidate architectures were compared against the actual dependency
structure of both upstreams:

**Option A — Ovis base, port T3 UI.** Keep Ovis's Bun backend and replace its
React client with a T3-style UI.

**Option B — T3 frontend, port Ovis's herdr connection.** Take T3 Code's
`apps/web` + `packages/contracts` + `client-runtime` and implement a server
that speaks T3's wire contract backed by herdr.

**Option C — new minimal bridge + new T3-styled client.** A small dedicated
Bun bridge to herdr's unix-socket/named-pipe API, and a fresh Vite/React
client built on T3's design system.

## Decision

**Option C.**

Reasons, from the code:

- T3 Code's client is not a skin over a generic API. `apps/web` reads
  `packages/contracts` schemas and `packages/client-runtime` atoms whose
  domain model is projects → threads → turns, backed by an event-sourced
  orchestration engine (`apps/server`). herdr's domain model is
  workspaces → tabs → panes → terminal streams + agent status. There is no
  honest mapping: threads, turns, checkpoints and provider sessions do not
  exist in herdr, and synthesizing them would fabricate data the UI then
  presents as real — explicitly forbidden by the project scope.
- Option B therefore degenerates into reimplementing T3's contract and
  runtime anyway, while inheriting its Effect-TS server, auth/pairing,
  provider registry and multi-surface machinery — all out of scope.
- Option A inherits Ovis's entire product surface (machines, relay, account
  pairing, per-agent transcript pipelines, PWA push, updater). The new
  project's scope is herdr session GUI only; forking and stripping that
  surface is a larger, riskier change than writing a narrow bridge.
- Option C keeps herdr as the sole authority for sessions, panes and agent
  state. The bridge is small enough to hold the proven invariants (one RPC
  per call, attach-stream truth, draft-on-disconnect, prompt-answer API)
  as explicit, testable code.

T3 fidelity is preserved where it matters: the UI primitives, theme tokens,
and composition rules are vendored/ported from T3's real implementation
(MIT), not approximated. T3's data-coupled components (ChatView, thread
lists, composer runtime) are not reused because their contracts have no
herdr counterpart; herdr equivalents are built from the same primitives.

## Consequences

- `server/` is a new, minimal Bun bridge. It re-implements the herdr wire
  protocol (NDJSON RPC, one connection per call, `events.subscribe`,
  Windows named pipe) rather than importing Ovis code.
- `src/` is a new Vite + React 19 app. `src/components/ui/` and
  `src/index.css` tokens are vendored from T3 Code with attribution.
- Any future need for Ovis-grade features (mirrored panes, relay, mobile)
  is a separate ADR, not an assumption of this architecture.
