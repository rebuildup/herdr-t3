# ADR-0022: plugin exec env scrub — no ambient herdr targeting vars

- Status: Accepted
- Date: 2026-11-25
- Amends: ADR-0011 (plugin boundary execution semantics).
- Program: issue #188; ticket #270. Upstream:
  rebuildup/herdr-plugins#83 (OPEN).

## Context

A herdr-t3 server launched inside a herdr pane (or a plugin runtime)
inherits the pane/plugin environment: `HERDR_SOCKET_PATH`,
`HERDR_SESSION`, `HERDR_PANE_ID`, `HERDR_PLUGIN_CONTEXT_JSON`, and the
rest of herdr's runtime injection set. Upstream socket resolution
(`packages/herdr-client/src/socket.ts`) orders
`HERDR_SOCKET_PATH` env > `--session`/`HERDR_SESSION` > default socket —
so an ambient `HERDR_SOCKET_PATH` overrides even the explicit
`--session` the bridge appends for named sessions, and pane selection
env beats positional pane ids for some commands. Every mutation
(`scripts stop`, `checkpoints restore`, git stage/commit/push,
`pr create`) could then hit a foreign Host/Session/Pane.

The pre-#270 scrub (`PLUGIN_ENV_SCRUB`) covered only
`HERDR_PANE_ID`/`HERDR_PLUGIN_CONTEXT_JSON`, applied only to contract
calls — discovery (`herdr plugin list`, which resolves a socket itself)
and capability probes passed no `envRemove` at all, and the SSH path
blanked variables (`VAR=''`) rather than removing them.

## Decision

1. **Scrub list mirrors herdr's own runtime scrub.** `PLUGIN_ENV_SCRUB`
   (exported from `server/plugins.ts`) covers socket/session targeting
   (`HERDR_SOCKET_PATH`, `HERDR_CLIENT_SOCKET_PATH`, `HERDR_SESSION`),
   pane identity (`HERDR_PANE_ID`, `HERDR_WORKSPACE_ID`,
   `HERDR_TAB_ID`, `HERDR_PLUGIN_CONTEXT_JSON`) and the plugin-runtime
   injection set (`HERDR_BIN_PATH`, `HERDR_ENV`, `HERDR_PLUGIN_*`),
   matching `scrub_herdr_runtime_env` in herdr's
   `src/cli/plugin.rs`.
2. **Every exec kind scrubs identically.** `plugin_list` discovery,
   `capability` probes and contract calls all pass the same
   `envRemove: PLUGIN_ENV_SCRUB`; explicit `--session` appending is
   unchanged.
3. **Removal, not blanking.** Local spawn deletes the keys. The SSH
   POSIX path emits `unset NAME ...;` (portable; `env -u` is
   GNU-only), and the PowerShell path keeps `$env:NAME=$null`, which
   deletes the variable from the process environment. Blanking was
   rejected because the `herdr` binary treats a *present* env var —
   even empty — as set (`var_os(...).is_some()`), while the plugin
   CLIs' falsy checks happened to tolerate it; removal is correct for
   both consumers. Scrub tokens run inside the remote command, after
   any login-shell profile could have re-exported the variables.
4. **Env names are validated** (`^[A-Za-z_][A-Za-z0-9_]*$`) before
   interpolation into remote command strings.

## Consequences

- No ambient env var can redirect a `plugin_call` (or discovery) to a
  different herdr session/socket/pane than the explicit
  machine + session + args specify; contract tests fail if the scrub
  list or any exec kind regresses (`server/plugins.test.ts`,
  `server/machines.test.ts`).
- Plugin CLIs fall back to their computed config/state dirs
  (`HERDR_PLUGIN_CONFIG_DIR`/`_STATE_DIR` scrubbed) — identical to
  what herdr itself injects, so no behavior change on clean hosts.
- XDG/HOME-derived defaults (`XDG_CONFIG_HOME`, `HOME`, `APPDATA`, …)
  are intentionally kept: they locate the *correct* host's herdr dirs
  and cannot override explicit flags.
- The SSH bridge commands themselves (`remote-api-bridge` /
  `remote-client-bridge`) remain unscrubbed: they already pass
  `--session` explicitly and remote env comes from the remote login
  shell, not the herdr-t3 server env. Revisit if upstream reports the
  same precedence issue for bridge resolution.
