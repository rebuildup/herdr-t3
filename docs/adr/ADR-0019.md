# ADR-0019: Projects/Scripts — projects-v1 re-pin @3b28349 (durable completion receipt)

- Status: Accepted
- Date: 2026-11-25
- Amends: ADR-0014/ADR-0015 (projects-v1 adoption point); same re-pin
  rule as ADR-0012/ADR-0015.
- Program: issue #188; ticket #265. Upstream: rebuildup/herdr-plugins#68
  (merged to release-0-3-0 @ `3b28349`). Upstream #67 (shell-portability
  PR #82) is still open and intentionally not consumed.

## Context

`docs/contracts/projects-v1.md` advanced after the ADR-0015 pin
(`b0c8c60`). **Response shapes are unchanged** — every field the client
parses (`ScriptRun` schema v2, outcomes, `scripts results`/`logs`
envelopes) is identical. The delta is run-record *lifecycle*:

- The runner emits a durable completion receipt —
  `__HERDR_DONE_<run-id>__=<code>` — into the owned pane's scrollback.
- `scripts results`/`logs` lazily re-scan that scrollback
  (`pane.read`, `recent_unwrapped`, last 2000 lines) after ownership
  re-validation and finalize a timed-out `running` record to
  `success`/`failed` with `exit_code`, `finished_at`, and a bounded log
  tail — across CLI invocations and herdr restarts, with no polling or
  daemon (`events.subscribe` `pane.output_matched` was evaluated and
  rejected upstream: a one-shot CLI cannot hold a subscription).

## Decision

1. **Re-pin**: herdr-t3 consumes `herdr-plugins.projects/v1` as
   implemented at `rebuildup/herdr-plugins@3b28349` (release-0-3-0).
   No parser, argv, or gating change is required — verified against the
   upstream diff (`plugins/projects/src/cli.ts` untouched; only
   `runner.ts` and the contract doc changed).
2. **Client stays pull-based**: the dialog already refetches
   `scripts results` on open/refresh and after `scripts stop`, and
   `scripts logs` on demand; each fetch now may return a finalized
   record. The client renders records exactly as returned and never
   upgrades `running` itself — honest-state rules (ADR-0014/0015)
   unchanged.
3. **Spec updated**: `docs/migration/contracts/plugin-projects.md`
   records the receipt semantics so "`running` may finalize on refresh"
   is documented behavior, not a surprise.

## Consequences

- A `running` record can legitimately become `success`/`failed` between
  two refreshes; the UI needs no change because it never caches a
  terminal state optimistically.
- `unknown` (vanished pane) semantics are unchanged — the receipt scan
  only runs for OWNED panes after ownership re-validation.
- ADR-0014 scope and ADR-0015 schema-v2 decisions stand.
