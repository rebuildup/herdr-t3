- Date: 2026-12-02

  `rebuildup.mcp`; same ADR-0011 `plugin_call` boundary as
  ADR-0012/0014/0016/0026–0031.
- Pin: `rebuildup/herdr-plugins@d23205af0cd2ff7dba25f72e1f3b872762a108ee`
  = tag `v0.9.0`. Upstream specs:
  `herdr-plugins/docs/contracts/secrets-v1.md`,

## Context

Three published plugin contracts had no GUI surface. Each carries a
distinct trust posture that a single ADR must fix before
implementation:

1. **secrets-v1** resolves declared env bindings against Infisical
   and routes values to exactly two sinks: a wrapped child's
   environment (`run`) and herdr surface-creation `env` params
   (`inject`). The contract guarantees no command ever returns,
   logs, persists, or argv-carries a resolved value, and provider
   stderr/stdout are never echoed into envelopes. The plugin
   advertises mutations (`run`, `inject` in `commands`; no
   `mutation_commands` field at v0.9.0).
2. **machines-v1** is read-only by upstream ADR-0028: live
   `herdr machine list` merged with last-known probe metadata
   (`list`, never probes) plus an on-demand live `probe`
   (SSH + remote api snapshot + remote plugin list — slow by
   design). `mutation_commands` is empty.
3. **mcp-v1** is a stable local-stdio MCP server contract. Its CLI
   surface is only `capability`/`serve`/`help`; mutations are MCP
   tools gated server-side inside `serve`, not CLI commands.

## Decision

1. **Secrets: value guarantee enforced twice.** Field-by-field
   `*FromDoc` parsers build models that structurally cannot carry a
   value (unit-tested with a planted `sk-live-…` sentinel that must
   not survive `JSON.stringify(model)`), and the argv builders
   (`secretsResolveArgs`/`secretsRunArgs`/`secretsInjectArgs`) accept
   only binding names, flags and surface options — no value input
   exists. The UI renders binding metadata (`name`/`env`/`ref`/
   `projectId`), per-binding statuses and `env_names` only; provider
   output is never rendered regardless of contract.
2. **Secrets mutations: allowlist ∩ advertised commands.**
   `SECRETS_MUTATION_COMMANDS = ["run", "inject"]` — the only
   contract mutations this client offers, each behind an explicit
   confirmation dialog. `config` (incl. `--init`) is never offered;
   no eval/emit command exists in v1. When a future plugin emits
   `mutation_commands`, an explicit deny wins over `commands`.
   `run`'s child inherits plugin stdio which the `plugin_call`
   bridge cannot stream: a successful run surfaces only as a
   bridge-level `plugin_bad_output`/`plugin_error`. The UI reports
   "ran, output not streamed" — it never fabricates success.
   `resolution_failed` DOES return a proper contract error before
   the child starts and is rendered verbatim.
3. **Machines: read-only, probe on demand.** `list` is the eager
   per-machine read (cheap — never probes). `probe` is invoked only
   on explicit user action (per-row or all) with the maximum
   `plugin_call` timeout; probe outcomes are data (`ok|disabled|
   unreachable|unsupported_remote|error`, `plugin_surface`
   `supported|unsupported|unknown` rendered verbatim — `unsupported`
   means "unknown remote inventory", never "no plugins"). A `list`
   failure keeps the machine `ready` with `listError` and retains
   the last-good list. `MACHINES_MUTATION_COMMANDS` stays empty —
   the contract is read-only and gating fails closed.
4. **MCP: diagnostics only.** `capability` is the sole consumed
   command — session resolution, access levels + `t3_mapping`, the
   tool table (`access`/`read_only`/`status`/`backs_onto`), sibling
   plugin availability, `error_codes`, `upstream_gaps`, and
   `remote.status: excluded_v1` (tracking herdrdev/herdr#6199) are
   rendered verbatim. `serve` is never spawned and no MCP tool is
   invoked — this client is not an MCP client. Mutations are MCP
   tools inside `serve`, so `MCP_MUTATION_COMMANDS` is empty and
   gating fails closed by design.
5. **Shared store shape.** `src/shell/{secrets,machines,mcp}.ts`
   mirror the artifacts/textgen stores: per-machine
   `{status, capability, …}` state, `useSyncExternalStore`,
   defensive parsers rejecting foreign contracts, the shared
   `not_installed|disabled|incompatible|unreachable|error`
   taxonomy, TTL-cached capability (~30s/10s error), refresh on
   snapshot pushes (debounced 800ms) + machine-status/machine-list
   changes via `init*()` in `App.tsx`, last-good retention on
   refresh failure.
6. **Surface wiring** follows the established right-panel pattern:
   `rightPanelStore` union + `isSurface`, `RightPanel`
   icons/titles/content/add-actions, `CommandMenu` and
   `WorkspaceHeader` entries, T3 primitives/tokens only.

## Consequences

- Three right-panel surfaces land capability-gated per host; hosts
  without the plugins render honest `not_installed`/`disabled`/
  `incompatible` states.
- Secret values can never reach the DOM, clipboard, logs, or argv —
  enforced structurally and covered by unit tests; a future contract
  revision that adds an eval/emit command requires a successor ADR
  upstream before this client may consume it.
- `run` cannot stream child output through `plugin_call`; if output
  capture is ever needed it requires a new upstream contract
  (successor ADR), not a bridge workaround.
- MCP tool invocation / MCP-client UX, machines lifecycle UI, and
  secrets `config` management remain separate tickets.
- Contract pins are recorded here and in
  `docs/migration/contracts/plugin-{secrets,machines,mcp}.md` +
  `docs/migration/capabilities.json`; the machines contract is draft
  upstream — a breaking revision re-pins via a new ADR.
