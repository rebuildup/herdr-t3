# ADR-0003: UI stack and T3 port policy

- Status: Accepted
- Date: 2026-11-22

## Context

The requirement is T3 Code's real design quality — not a "T3-like" lookalike.
T3 Code's web UI is React 19 + Tailwind CSS v4 + Base UI + cva +
tailwind-merge, with React Compiler, strict primitive composition rules
(`docs/internals/web-ui.md`), and runtime theme tokens.

## Decision

- Stack: Vite + React 19 + TypeScript, Tailwind CSS v4, `@base-ui/react`,
  `class-variance-authority`, `tailwind-merge`, `lucide-react`, xterm.js 6
  for terminal surfaces. Bun is the package/runtime tool (matching the
  maintainer's toolchain); the production artifact is a static build served
  by the Bun bridge.
- Port policy:
  1. **Vendor** presentational primitives (`components/ui/*`) close to
     verbatim, keeping MIT attribution.
  2. **Port** theme tokens (`index.css` `:root`/`@theme` blocks) faithfully
     for the surfaces herdr-t3 ships; drop tokens for features that do not
     exist here, add herdr-specific tokens only when a surface needs them.
  3. **Re-implement** data-coupled components (sidebar lists, chat/composer
     equivalents) in herdr terms using the same primitives and tokens.
  4. **Never** copy T3 pixels from screenshots; verify against T3's real
     implementation and, for release candidates, side-by-side captures.
- herdr domain surfaces map to T3 design language as follows (design work
  continues under the UI issues):
  - Workspace list → sidebar navigation hierarchy (T3 project/thread list
    patterns, adapted to workspace → tab → pane).
  - Tab strip → T3 tab/panel chrome.
  - Pane grid → T3's resizable panel/split patterns where they exist;
    terminal regions stay real terminals.
  - Agent status → T3 state badges/labels, driven only by herdr's
    `agent_status` data.
  - Composer → only where herdr actually accepts text input
    (`pane.send_text`, `agent.prompt`); no fabricated thread composer.

## Consequences

- `src/index.css` and `src/components/ui/` are vendored material: edits
  should stay minimal and attributable; project-specific additions go in
  separate files or clearly marked blocks.
- Design verification is part of done-ness for UI tickets: component-level
  fidelity to T3 rules plus state-by-state review, not a single screenshot.
