# ADR-0008: Canonical UI architecture — T3 Code application shell

- Status: Accepted
- Date: 2026-11-23
- Amends: ADR-0003 (surface mapping section); supersedes the incremental
  "improve the existing Herdr UI toward T3" approach recorded in issues
  #52/#54/#36

## Context

The v0.2.x UI was built by improving the existing Herdr layout toward T3
Code's design language: ported primitives, vendored tokens, and local fixes
to sidebar/topbar. Issues #36/#52/#54/#56/#69 accumulated around that
approach. The result is a Herdr-shaped layout wearing T3 styling — not T3
Code's actual application structure.

T3 Code's real UI is an application shell, not a theme:

- `AppSidebarLayout` composes `SidebarProvider` + a resizable offcanvas
  `Sidebar` + a floating `SidebarControl` trigger + window-controls insets.
- The sidebar is `SidebarChrome`: a topbar-height drag-region header
  (brand, history navigation on Electron, environment identification), a
  searchable item list, and a footer utility row (Settings and domain
  utilities).
- Content routes render either utility pages inside `WorkspacePageContainer`
  with `SettingsSidebarNav`-style navigation, or a main view: a 52px
  drag-region header (breadcrumb + actions) above the work canvas.
- Desktop window chrome is part of the design: macOS `hiddenInset` with
  traffic lights positioned against the topbar, Windows `titleBarStyle:
  hidden` + `titleBarOverlay` (WCO), both collapsing in fullscreen.
- The command palette (⌘K), keyboard shortcuts, context menus and
  light/dark themes are shell-level behavior, not per-screen extras.

Herdr-t3's stack cannot adopt T3's data layer (`@effect/atom-react`,
TanStack Router, `gt-react` i18n, Effect contracts). What must be canonical
is the **screen structure and interaction model**, with herdr-t3's own
state layer behind it.

## Decision

1. **T3 Code's application shell is the canonical UI structure.** The
   screen is composed as `AppSidebarLayout`-equivalent regions: sidebar
   chrome (header/body/footer), inset content with a topbar-height
   drag-region header, utility pages with their own navigation, and the
   desktop window chrome contract above. Approximate "T3-style"
   rearrangements of the old layout are defects, same as approximate CSS.
2. **Fixture-first milestone.** The shell is reproduced completely with
   fixed dummy data — no herdr RPC — and accepted by side-by-side visual
   review against the pinned T3 Code implementation before any Herdr
   feature work resumes on it. Existing components that conflict with the
   canonical structure are replaced, not adapted around.
3. **Reuse boundary.** Primitives in `src/components/ui/` and theme tokens
   in `src/index.css` remain vendored T3 material (ADR-0003 policy
   unchanged). Shell-level components (`AppSidebarLayout`,
   `SidebarChrome`-equivalent, settings navigation, workspace header) are
   ported structurally and re-bound to herdr-t3 state; T3-only subsystems
   (threads, projects, providers, PRs, i18n, Effect atoms) are not ported.
4. **Herdr mapping is an information-design decision, not a hierarchy
   transplant.** Machine = connection environment; Workspace = the user's
   work unit (sidebar item); Tab/Pane = in-workspace view/operation units
   rendered inside the content area. Whether every level is always visible
   is decided per screen from T3's information design, not from the herdr
   TUI layout.
5. **Backend contracts are unchanged.** Bridge invariants (AGENTS.md §3),
   Ghostty engine (ADR-0007), session ownership, and Local/Remote
   connection contracts (ADR-0006) are preserved. This ADR changes only
   the presentation layer.
6. **Visual review is a gate.** Each milestone produces same-condition
   captures of T3 Code and herdr-t3, optimized to WebP and reviewed by an
   image-capable model for structure/density/operability — per
   `docs/design/verification.md` and the issue #69 pipeline.

## Consequences

- `docs/design/app-shell.md` is the canonical screen-structure spec;
  `docs/design/rules.md` remains the lint-level rule mapping.
- Issues #52/#54 are superseded by the redesign program (their ticket
  splits assumed the old layout as the base). #36's fidelity audit and
  #69's evidence pipeline remain valid and are reused. Issue acceptance
  criteria are preserved; only the baseline they measure against changes.
- Work lands on the next release line (`release-0-3-0`); v0.2.x tags are
  untouched.
- The old `App.tsx` composition, `AppSidebar`, `WorkspaceTopbar`,
  `PaneGrid` chrome and `WorkspacePageHeader` usage are replaced by the
  canonical shell; `PaneTerminal`/bridge code is untouched until the
  Herdr-mapping milestone.
