# ADR-0009: T3 Code feature-parity program (v0.6.0+)

- Status: Accepted
- Date: 2026-11-24
- Amends: AGENTS.md §5 scope boundary ("T3 orchestration/checkpoint/thread
  management" exclusion); extends ADR-0008's "T3 shell is canonical" to the
  feature surface.

## Context

v0.5.0's UI convergence (#156 program) reproduced T3 Code's *shell* —
sidebar, topbar, panels — but not its *feature surface*. A maintainer
review found that agent-harness rows lack provider icons, there are no
issue/PR lists, no usage tracking, and no right-panel surfaces comparable
to T3's. The directive is: implement **everything T3 Code has that does not
conflict with herdr**, then consider extracting the result as a herdr
plugin.

T3 Code's feature inventory spans: thread/chat orchestration, issue and
pull-request surfaces, usage metering and pricing, preview browser, device
panels, ~25 settings sections, diffs, file browser, search, scheduled
tasks, voice, MCP, and more (see `docs/design/t3-parity.md` for the full
mapping).

The herdr boundary remains absolute: herdr owns every pty, scrollback, and
agent state; herdr-t3 never owns sessions, providers, or orchestration.
Features that would require herdr-t3 to *become* the orchestrator conflict
with this and stay excluded.

## Decision

1. The scope boundary in AGENTS.md §5 is amended: T3 Code features that can
   be implemented **on top of** herdr's data model (display, navigation,
   metadata enrichment via external CLIs or future herdr upstream fields)
   are in scope for the v0.6.0+ parity program tracked by issue #188.
   Thread/checkpoint/orchestration *state ownership* remains out of scope.
2. `docs/design/t3-parity.md` is the canonical feature inventory: every
   T3 Code surface is classified by data source — (a) herdr-provided,
   (b) external CLI/integration (`gh`, agent CLIs), (c) herdr upstream
   extension required, or (d) excluded as orchestration-conflicting.
3. Implementation proceeds in phases per the inventory's priority order;
   each phase is its own top-level issue/PR cycle against the current
   release branch.
4. Features in class (c) are prepared as upstream proposals
   (herdrdev/herdr Ideas/discussions) rather than fabricated client-side.
5. The plugin-extraction question (herdr plugin packaging) is deferred to a
   separate ADR once the parity surface stabilizes; this ADR does not
   commit to it.

## Consequences

- herdr-t3 grows beyond a thin multiplexer client toward a T3-shaped
  workspace shell; the bridge stays thin — enrichment data lives in the
  client layer or external integrations, never in herdr session state.
- Where T3 assumes a backend that herdr does not provide (issues, PRs,
  usage), the client integrates `gh`/provider CLIs or waits on upstream —
  it does not fabricate the data (AGENTS.md §4 invariant preserved).
- Release v0.5.0 continues unaffected; the parity program targets v0.6.0+.
